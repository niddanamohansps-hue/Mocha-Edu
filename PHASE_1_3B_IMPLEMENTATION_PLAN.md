## 3. Migration Ordering and Dependencies

**Revised granularity: 6 migration files, one per app, not 13 (12) per table.** The initial draft proposed one migration per table/field on the theory that it gives independent per-table rollback. Checking that claim against this project's actual migration graph (confirmed in this revision by listing every touched app's existing migrations) shows it does not hold the way it was framed:

- Every touched app (`attendance`, `course_content`, `examinations`, `fees`, `students`, `timetable`) already has a strictly linear, app-local migration history (1–2 files each today) — Django migrations within one app are *always* applied and reversed in that app's own linear order; there is no cross-app ordering dependency today and none would be introduced by this phase. **Cross-app independence — the property that actually matters for "can I roll back table X's change without affecting table Y's" when X and Y are in different apps — already exists at the app level, with zero extra files needed.** Splitting further, to one file per table *within* the same app (e.g. `examinations` would otherwise get 4 separate migration files for Examination/ExamSchedule/ExamResult/GradeBoundary), buys a narrower rollback grain only within that single app, at the cost of 4 extra files, 4 extra dependency edges, and 4 separate deploy-time migration steps to track — for a rollback scenario (reverting one field's column while keeping its sibling field's column in the same app) that this plan has no concrete reason to expect, since any problem serious enough to need reverting Stage A is far more likely to be a project-wide issue (wrong FK target, wrong `on_delete`, PostgreSQL version incompatibility) caught at Stage A's gate (§11) before Stage B/D ever touches data — not a single-table-only problem needing single-table-only reversal.
- **Revised plan: one migration per app, containing every `AddField` operation for that app's own FK field(s)**, all as `null=True, on_delete=models.PROTECT`:

| Migration | App | AddField operations |
|---|---|---|
| `attendance/migrations/0002_add_academic_year_ref.py` | attendance | `AttendanceSession.academic_year_ref` |
| `course_content/migrations/0003_add_academic_year_ref.py` | course_content | `SubjectEnrollment.academic_year_ref` |
| `examinations/migrations/0002_add_academic_year_ref.py` | examinations | `Examination.academic_year_ref`, `ExamSchedule.academic_year_ref`, `ExamResult.academic_year_ref`, `GradeBoundary.academic_year_ref` |
| `fees/migrations/0002_add_academic_year_ref.py` | fees | `FeeStructure.academic_year_ref`, `StudentFee.academic_year_ref` |
| `students/migrations/0003_add_academic_year_ref.py` | students | `StudentLevel.academic_year_ref`, `PromotionRecord.source_academic_year_ref`, `PromotionRecord.target_academic_year_ref` |
| `timetable/migrations/0002_add_academic_year_ref.py` | timetable | `Period.academic_year_ref`, `TimetableEntry.academic_year_ref` |

Each of the 4 multi-field migrations (examinations, fees, students, timetable) remains a single migration reversible as one unit — Django's `AddField` operations within one migration are each independently listed and the migration as a whole reverses cleanly (dropping all its columns together), which this plan accepts as the correct rollback grain per the reasoning above. If, during implementation, a genuine reason emerges to isolate one specific field's rollback from its siblings in the same app (e.g. one field's backfill proves far riskier than the others), that single field can still be pulled into its own follow-up migration at that time — this is not foreclosed, just not pre-built speculatively.
- **Dependency ordering**: each of the 6 migrations depends on (a) its own app's latest existing migration, and (b) `academics.0002_academicyear` (the migration that created the `AcademicYear` model). The 6 migrations have no dependency on each other and can be applied in any order, or in parallel across apps.
- **Model state stays synchronized with migrations** the standard Django way: each model gets its new field(s) added in the same change as its app's migration. `manage.py makemigrations --check --dry-run` must pass after each of the 6 migrations is authored, not only once at the end of the batch, to catch drift immediately.
- No migration in this phase touches `unique_together`, adds a DB index beyond what Django auto-creates for the FK itself, or alters the legacy column — those remain Step F (§9), gated separately.
- **django-tenants consideration**: these are tenant-schema migrations (all 13 fields live in tenant-local tables, confirmed in Phase 1.3A §7), so they apply via `migrate_schemas` (or the project's equivalent django-tenants migration command) across every tenant schema, not plain `migrate`. The excluded tenants (`spsghy`, `test_chk`) still receive the schema change (empty tables gaining a nullable column is schema-only, harmless, and keeps them schema-consistent with included tenants) — only the **data backfill** (§4) is tenant-scoped to the two approved tenants, not the schema migration itself.

## 4. Tenant-Scoped, Idempotent Backfill Design

Extends `academics/backfill.py` rather than duplicating it — the existing `DECISIONS`, `validate_decisions()`, and the `tenant_context()`-per-tenant pattern in `apply_tenant()`/`validate_tenant()` are the template.

- **New function per table**, not one generic loop over `LEGACY_FIELDS` — each of the 13 fields has a different model import, different FK field name (`academic_year_ref` vs `source_academic_year_ref`/`target_academic_year_ref`), and potentially a different "what counts as already done" check. A generic loop driven purely by `(table, column)` strings (as `validate_tenant`'s raw-SQL approach does for read-only validation) is appropriate for read-only introspection but not safe for writes — explicit per-model code makes the backfill auditable and lets each table's edge cases (PromotionRecord's empty-string target; GradeBoundary's exception) be handled in code, not string-matched generically.
- **Idempotency contract**: a backfill function for table T only ever updates rows where `academic_year_ref IS NULL` (or, for `PromotionRecord.target_academic_year_ref`, rows where `target_academic_year != "" AND target_academic_year_ref IS NULL`) **and** the legacy string value has a resolvable mapping. Re-running the command after a full or partial success is a strict no-op for already-resolved rows — mirrors `apply_tenant`'s existing-row check pattern.
- **Tenant scoping**: each table's backfill runs inside `with tenant_context(org):` for each tenant in `INCLUDED_TENANTS` only (`greenvalley_demo`, `sunrisevalley_school` today) — never `spsghy`/`test_chk`, consistent with `EXCLUDED_TENANTS` in the existing module. A future onboarding of those tenants requires its own explicit decision block (same standing rule carried from Phase 1.2D and restated in Phase 1.3A §7), not an assumption that this phase's backfill logic silently extends to them once they gain data.
- **Mapping source**: the exact same `DECISIONS[tenant]["mapping"]` dict already defined and re-verified clean (`unmapped=[]`, `ambiguous=[]`, `orphan_rows=[]`) in Phase 1.2D/1.3A. No new mapping is introduced or re-derived — this backfill is a mechanical application of an already-approved mapping, table by table, not a new business decision.
- **Consistent mapping semantics with dual-write (fixes a correctness bug found in this revision's review)**: every per-table backfill function resolves a row's FK by calling the same `resolve_academic_year_fk(tenant, legacy_value)` two-step function defined in §7 (mapping lookup → `AcademicYear.name` lookup), never a direct `AcademicYear.objects.get(name=legacy_value)` shortcut. This matters concretely for Green Valley, whose approved mapping is `"2025" → "2024-25"` and `"2026" → "2025-26"` — a direct-by-name lookup would silently fail to resolve every Green Valley row. Backfill and dual-write sharing one resolution function (not two independently written copies) is what guarantees they can never drift into different mapping behavior over time.
- **The documented GradeBoundary exception is applied as an exact, pinned predicate, not a count.** The backfill function for `GradeBoundary` must, before resolving any row, check it against this precise set — tenant `sunrisevalley_school`, table `examinations_gradeboundary`, legacy `academic_year="2024-25"`, and these exact primary keys (captured directly from the database in this planning phase, not estimated):

  ```

  c329f96b-6237-4aa5-9e7c-d93a907be9b0  (grade_label="C",  min=35.00, max=49.99)
  1cb765f0-8221-4920-bcaa-f965750d62f5  (grade_label="B",  min=50.00, max=64.99)
  ```

  The backfill code should hard-code this exact ID list (or re-select it by the equivalent precise predicate `tenant=sunrisevalley_school AND academic_year="2024-25"` at run time and assert the resulting ID set equals this list before treating them as the exception) — **any row matching `academic_year="2024-25"` in `sunrisevalley_school` whose ID is NOT in this list is treated as an unexpected unmapped row and fails gate 1 (§6)**, not silently folded into the exception. This closes the gap in the original draft, where "allow nulls for six rows" could have been misread as "allow nulls for any row that happens to count to six" — it is specifically these six rows, identified by primary key, and no others, ever.
- **No cross-table inference**: each table's backfill resolves its OWN row's legacy string independently through the mapping (Phase 1.3A §5's explicit requirement) — it never copies a resolved FK from a related row (e.g. does not set `StudentFee.academic_year_ref` from the linked `FeeStructure.academic_year_ref`). This is deliberate: it means any pre-existing StudentFee/FeeStructure mismatch (Decision 1) surfaces as two independently-resolved, potentially-different FKs, which is exactly what the mismatch report (§6) must detect and report, not silently harmonize.

### 4.1 `StudentLevel.academic_year_ref` Backfill Concurrency Strategy

`StudentLevel` is singled out because it is the one table whose rows are also locked by a live, concurrent, business-critical transaction — promotion (`execute_lifecycle_actions` in `backend/students/services.py`) — unlike the other 12 tables, which have no comparable concurrent-writer locking pattern in the codebase today. This section resolves that risk with a concrete design, grounded in two facts confirmed by a targeted, read-only check performed in this revision (not assumed):

**Evidence gathered:**
1. `students/services.py`'s `_lock_current_rows()` function already locks exactly the `StudentLevel` rows a promotion batch needs via `select_for_update()`, filtered to `is_current=True` for the batch's student IDs, and — critically — **in stable ascending `student_id` order** (`.order_by("student_id")`), with a code comment explicitly stating this matches `fees.services.record_payment`'s own deadlock-avoidance discipline. This is an existing, deliberate, documented convention in the codebase, not something this plan is inventing.
2. `config/settings.py`'s `DATABASES["default"]` block has **no `OPTIONS` entry at all** — no `lock_timeout`, no `statement_timeout`, nothing. This was confirmed by reading the settings file directly in this revision. **There is no existing project-wide convention for lock-wait timeouts, retries, or deadlock handling to reuse** — by default, PostgreSQL waits indefinitely for a contended row lock, and Django/psycopg2 will raise `django.db.utils.OperationalError` wrapping a `psycopg2.errors.DeadlockDetected` only if PostgreSQL's own deadlock detector fires (which requires an actual cycle, not just a long wait) — a plain lock wait against a long-running promotion transaction would otherwise block the backfill batch indefinitely with no existing timeout to bound it.

**Recommended design, based on this evidence (not requiring further audit — the two facts above are sufficient to settle it):**
- The `StudentLevel` backfill's batched `.update()` (§5) must **lock the rows it is about to update** via `select_for_update()` before updating them — not rely on a bare `.update()`'s implicit row-level locking alone — and must do so **in the same stable ascending `student_id` order** `_lock_current_rows()` already uses. Locking in the same, already-established order as promotion is what actually prevents a deadlock between the two (a deadlock requires two transactions to lock the same rows in *different* orders; matching promotion's order removes that possibility by construction, rather than merely reducing its likelihood).
- Because no project-wide `lock_timeout` exists, the backfill must set one **scoped to its own transaction only** — `SET LOCAL lock_timeout = '5s'` (or an equivalent explicit, short, configurable value) issued at the start of each backfill batch's `transaction.atomic()` block. `SET LOCAL` is transaction-scoped in PostgreSQL and automatically reverts at commit/rollback, so this does not change behavior for promotion's own transactions, any other code path, or any other table's backfill — it is strictly additive to the `StudentLevel` backfill's own batches, consistent with the instruction to avoid changing promotion's business rules or adding any new global constraint.
- **Lock timeout (expected behavior)**: if the backfill's `select_for_update()` cannot acquire a row lock within the scoped timeout (because a promotion transaction is actively holding it), PostgreSQL cancels the statement. The backfill's batch-level `transaction.atomic()` (already specified in §5) rolls back automatically and cleanly — no partial writes within that batch. The batch is retried a small, fixed number of times (recommended: 3 attempts) with a short, increasing backoff (e.g. 1s, 3s, 9s) before being skipped and explicitly reported as "deferred — contended, retry on next run" (never silently dropped and never counted as resolved). Because the backfill is idempotent and `IS NULL`-gated (§5), simply re-running the command later resolves any deferred batch once the contending promotion transaction has committed — no special resume bookkeeping is needed beyond what §5 already provides.
- **Deadlock (expected behavior)**: in the unlikely event PostgreSQL's own deadlock detector fires (a genuine lock-ordering cycle, which matching promotion's lock order is specifically designed to prevent, but which this plan does not claim to make structurally impossible — only parallel ordering plus a bounded timeout together make it very unlikely), the batch's transaction has already been rolled back by PostgreSQL itself, the batch is retried with the same backoff policy, and a batch that still fails after the retry budget is deferred and reported, not force-written or skipped silently.
- **Error classification (revised — corrects a verified discrepancy found in the Pre-Stage-B Readiness Audit)**: the retry/backoff behavior above applies only to two specific, narrowly-identified conditions — a lock-wait timeout caused by this batch's own `SET LOCAL lock_timeout`, and a genuine deadlock.

  **Evidence basis for this revision**: the Pre-Stage-B Readiness Audit (prior to this plan revision) ran a safe, non-mutating, immediately-rolled-back diagnostic directly against this project's live PostgreSQL 18.4 + psycopg2 2.9.13 stack, reproducing all three relevant conditions by locking real rows inside transactions that were never committed. This plan revision cites that audit's findings as its evidence; it does not itself re-run the diagnostic. The audit's three confirmed results:

  | Scenario | Exception class | SQLSTATE | Message |
  |---|---|---|---|
  | Row-lock timeout (`SELECT ... FOR UPDATE` blocked, `lock_timeout` expires) — **this batch's actual target scenario** | `psycopg2.errors.LockNotAvailable` | **`55P03`** | `"canceling statement due to lock timeout"` |
  | `statement_timeout` expiring (contrast case) | `psycopg2.errors.QueryCanceled` | `57014` | `"canceling statement due to statement timeout"` |
  | Deadlock | `psycopg2.errors.DeadlockDetected` | `40P01` | `"deadlock detected"` |

  This corrects the plan's previous assumption (Revision 5) that a row-lock timeout produces SQLSTATE `57014` requiring message-text disambiguation. On this project's verified stack, a row-lock timeout instead produces the **structurally distinct** SQLSTATE `55P03` (`lock_not_available`), which does not collide with `57014` or `40P01` at all — no message-text matching is needed for this condition.

  - **Lock-timeout retry condition (corrected)**: `pgcode == '55P03'` (`psycopg2.errors.LockNotAvailable`). This SQLSTATE is specific to "could not obtain lock" conditions and is sufficient on its own — no message-text check is required for this condition, unlike the prior (incorrect) design.
  - **Deadlock retry condition (unchanged)**: `pgcode == '40P01'` (`deadlock_detected`) — this SQLSTATE is specific to deadlocks and needs no message-text check. Not affected by this correction.
  - **`57014` (`query_canceled`) is evaluated separately and is NOT classified as retryable by this plan.** The audit confirmed `57014` is produced by `statement_timeout` expiry (and, per PostgreSQL's documentation, also by a manual `pg_cancel_backend()` and other statement-cancellation causes) — it is a generic "this statement was cancelled" code, not specific to any one cause, and the audit did not test every possible cause of it. **This plan does not classify any `57014` as retryable.** Whether a narrowly message-gated secondary retry condition for `57014` (e.g., in case some other PostgreSQL code path produces `57014` with lock-timeout-like wording instead of `55P03` in some circumstance not covered by the audit) would be appropriate is **left explicitly unresolved by this plan** — the available evidence (one verified scenario on one stack/version combination) is insufficient to decide this either way, and this plan does not guess. If an implementer later encounters a real `57014` case that should have retried, that is new evidence requiring its own review before any `57014` handling is added — not something to resolve speculatively now.
  - **Everything else propagates immediately, uncaught by the retry loop** — any bare `57014`, any other `OperationalError`, a constraint violation, a connectivity failure, or a programming error in the batch's own query. The implementation must catch `django.db.utils.OperationalError`, inspect `.__cause__.pgcode` for exactly `55P03` or `40P01`, retry only on those two, and re-raise everything else unmodified. A bare `except Exception` or `except OperationalError` with no further discrimination is explicitly disallowed by this design.
  - **Remaining assumptions, stated explicitly (not resolved by this plan)**: the audit verified this signature on PostgreSQL 18.4 with psycopg2 2.9.13, using a `SELECT ... FOR UPDATE` row-lock wait specifically. It did not test: other PostgreSQL versions, psycopg3 (should this project ever migrate drivers), non-English server locales, or whether a `lock_timeout` expiring while waiting for a lock type other than a row-level tuple lock (e.g., a table-level lock from a different code path) might still produce `57014` instead of `55P03`. This plan's classifier is scoped to the verified scenario (`StudentLevel`'s row-level `select_for_update()` batch) and makes no claim beyond it. Per the earlier "message-matching is not a universally portable interface" caution (still applicable in spirit, now applied to the SQLSTATE itself rather than message text): **isolate this classifier inside one small, independently unit-tested function** (e.g. `is_retryable_lock_contention(exc) -> bool`, checking `pgcode in {'55P03', '40P01'}`), never inlined ad hoc at each call site, so a future PostgreSQL/driver change has exactly one place to update and one test to re-run. **Fail closed**: if the classifier does not positively recognize the exception as one of these two exact codes, it returns `False` and the error propagates uncaught, rather than defaulting to "retry when unsure."
- **Retry-after-rollback ordering (tightened in this revision)**: because each batch is already wrapped in its own `transaction.atomic()` (§5), Django guarantees the transaction is fully rolled back by the time the `OperationalError` propagates out of the `atomic()` block — there is no window where a retry could begin while the failed transaction's locks or partial state are still held. The retry loop must sit **outside** the `atomic()` block (re-entering a fresh `atomic()` context for each attempt), never inside it — retrying inside the same atomic block would retry against an already-poisoned, half-rolled-back transaction, which Django does not support (a transaction that has seen a database error must be abandoned, not reused).
- **Same-rows guarantee (tightened in this revision)**: the batch's `select_for_update()` lock acquisition and its subsequent `.update()` (or `bulk_update()`) must operate against the **exact same primary-key set**, computed once at the start of the batch attempt and reused for both the lock query and the write query — not two independently-evaluated queries against the same filter conditions, which could (in principle, under concurrent modification) select a different row set the second time. The recommended implementation: materialize the batch's target IDs into a list (`list(queryset.values_list("id", flat=True))`) once, lock by `StudentLevel.objects.select_for_update().filter(id__in=batch_ids).order_by("student_id")` (preserving the same stable order `_lock_current_rows()` uses), and then update only those same `batch_ids` — never re-deriving the "next unresolved batch" filter a second time mid-attempt.
- **What this design deliberately does NOT do**: it does not add a database-level constraint of any kind (no new unique constraint, no check constraint — consistent with the standing instruction to avoid schema changes beyond the nullable FK itself), it does not change `execute_lifecycle_actions` or `_lock_current_rows` in any way (promotion's code and business rules are completely unmodified — the backfill adapts to promotion's existing locking discipline, not the other way around), and it does not attempt to resolve the separately-tracked, broader risk that `StudentLevel` has no DB-level single-current-row invariant (Phase 1.3A §3.5, restated in §12's risks below) — that remains a distinct, larger concern this plan continues to treat as out of scope, not something the backfill's locking strategy is meant to paper over.
- **This item is resolved in this revision, not marked blocked** — the two evidence points above (promotion's existing lock-order convention; the absence of any existing timeout convention) are sufficient to settle a safe, concrete design without requiring further codebase audit. If an implementer later finds additional concurrent writers of `StudentLevel` beyond promotion that this plan has not accounted for, that would be new evidence warranting a return to this section, but nothing uncovered in this revision's check points to such a gap.

## 5. Dry-Run Behavior, Batching, Progress Reporting, Error Handling, Safe Reruns

- **Dry-run is the default**, mirroring `backfill_academic_years`'s own `--apply` convention. The new command (name proposed: `backfill_academic_year_fks`) prints, per table per tenant: total rows, rows already resolved (skip), rows about to be resolved (with the target `AcademicYear.name`), and rows that cannot be resolved (grouped by distinct unmapped value, with a count) — never row-by-row for large tables, to keep dry-run output readable even for a table with thousands of rows.
- **Batching**: each table's actual write uses `.update()` in chunks keyed by primary-key range or `iterator(chunk_size=...)` + `bulk_update`, not one `UPDATE ... WHERE` touching an unbounded row set in a single statement when row counts are large (the demo tenant alone has 1,900+ `ExamResult` rows and 3,960 `AttendanceSession` rows per the Phase 1.3A audit — real tenants could be larger). A conservative default batch size (e.g. 500–1000 rows) with a `--batch-size` override is recommended, each batch in its own `transaction.atomic()` block so a failure partway through a table only requires reprocessing from the last completed batch, not the whole table.
- **Progress reporting**: one log line per batch (table, tenant, batch range, rows updated, rows skipped/unmapped within that batch), plus a final per-table-per-tenant summary line. This mirrors the existing `backfill_academic_years` command's `self.stdout.write` pattern, extended for batch granularity.
- **Error handling**: any row whose legacy value is NOT in the tenant's mapping and is NOT a documented exception (§6) is skipped and counted, never defaulted to any FK value and never causes the whole batch/table to abort — but the command's final exit must reflect whether any unexpected-unmapped rows were found (non-zero exit code or an explicit `UNRESOLVED ROWS FOUND` summary line) so this cannot be mistaken for full success in a deployment pipeline that only checks the exit code.
- **Safe reruns**: because the write is `WHERE academic_year_ref IS NULL`-gated and the mapping is static, rerunning the exact same command after an interrupted run (process killed, DB connection dropped mid-batch) resumes correctly — already-set rows are skipped, the interrupted batch's partial transaction was rolled back entirely (nothing half-written within one batch, since each batch is one atomic block), and the next run simply continues from the first still-NULL row. No separate "resume from checkpoint" bookkeeping table is needed given this design — the `IS NULL` predicate IS the checkpoint.

## 6. Validation Gates

Four gates, each must pass before the next stage proceeds — this plan treats them as a strict sequence, not parallelizable checks, because gate 4 (the mismatch report) specifically depends on gate 1's FKs already being populated on both sides of the relevant relationship.

1. **Unmapped rows** — for every table/tenant, any row whose legacy string is not in `DECISIONS[tenant]["mapping"]` and not a documented exception (gate 2) is reported by exact value and count. Zero tolerance: this gate fails (blocks proceeding to Step D) if any unexpected unmapped row exists anywhere in the two included tenants, since Phase 1.2D/1.3A already established the mapping is complete for all data present at audit time — a new unmapped value appearing here means either new data was written between audit and backfill (a timing issue to investigate, not paper over) or the mapping audit missed something (a correctness issue to escalate, not guess past).
2. **The six documented exceptions** — `GradeBoundary` rows in `sunrisevalley_school` with legacy `academic_year="2024-25"` (exactly six, per Decision 6) are confirmed present, confirmed to remain exactly six, and confirmed to resolve to `academic_year_ref = NULL` by design, not by failure. A regression assertion (§10) locks this count so a future data change can't silently grow or shrink this "allowed null" set without someone noticing.
3. **FK integrity** — standard Django `AcademicYear`-pointing FK referential integrity (guaranteed by the DB once the constraint exists) plus an explicit tenant-isolation check: no FK on any of the 13 tables in tenant A ever points to an `AcademicYear.id` that belongs to tenant B. Structurally this is already impossible (schema-per-tenant means tenant B's `AcademicYear` rows live in a different schema's table entirely, so a cross-schema FK reference cannot even be constructed), but the validation gate still asserts it as a positive test (§10) rather than relying purely on "it's structurally impossible" as the only line of defense.
4. **StudentFee–FeeStructure mismatches (Decision 1) — report only; enforcement is explicitly out of this phase.** Once both `StudentFee.academic_year_ref` and `FeeStructure.academic_year_ref` are populated (via the linked `StudentFee.fee_structure` FK, for rows that have one), report every `StudentFee` whose resolved `academic_year_ref` differs from its linked `FeeStructure`'s `academic_year_ref`, grouped by tenant, with student/fee identifiers for follow-up — **and do not rewrite any of them, and do not reject or block any write because of them.**

   **Resolving the apparent conflict between Decision 1's two halves**: Decision 1 says both "require match" and (via this plan's own non-blocking dual-write design, §7) "never block an existing write." These are not actually in tension once sequenced as two separate steps rather than one:
   - **This phase (non-blocking, included here)**: produce the mismatch report (read-only, §6 gate 4) and, in the dual-write code (§7), simply set each row's own FK independently — exactly as every other table's dual-write does, with no StudentFee-specific special case. A pre-existing or newly-created mismatch is recorded by the report; it is never blocked, corrected, or rejected by this phase's code.
   - **A separately gated future step (explicitly NOT part of this phase, requires its own review and approval)**: after the mismatch report has been reviewed by a human and a resolution policy is decided for the pre-existing cases it found (accept as historical fact / correct via a reviewed data fix / something else — Decision 1 explicitly defers this choice), *that* future step is where "require match going forward" becomes an actual enforced validation (e.g. a service-layer check in `assign_student_fee()` rejecting a new StudentFee whose submitted year disagrees with its FeeStructure's year). This plan does not write that validation and does not pick its resolution policy — it only guarantees the report exists and is reviewable, and that today's dual-write never pre-empts that future decision by silently blocking or correcting anything now.
   - This split is what makes the phase's "never block an existing write" guarantee (§7) and Decision 1's "require match" instruction compatible: non-blocking is a property of *this* phase's code; enforcement is a property of a *different*, later, separately-approved phase. The plan originally stated both without drawing this line explicitly, which is the gap this revision closes.

## 7. Dual-Write Design

- **Authoritative field during the entire Phase 1.3B window: the legacy string field.** The FK (`academic_year_ref`) is write-accompanying, never write-primary, until a future, separately-approved phase flips this (Phase 1.3A §8 Step D/E, reaffirmed here — this plan does not propose making the FK authoritative within 1.3B's own scope, since doing so would require exactly the validation-hardening and frontend-contract decisions marked out-of-scope by Decisions 3 and 5).
- **Write ordering within a single request/service call**: write the legacy string field first (exactly as today, unchanged), then resolve and set the FK **in the same transaction**, using the **same resolution function the backfill uses (§4)** — never a direct `AcademicYear.objects.get(name=<the legacy string>)` lookup.

  **Corrected resolution algorithm (fixes a bug in the prior draft)**: the prior draft of this section proposed looking up `AcademicYear` by `name` equal to the legacy string value just written. This is incorrect for tenants whose approved mapping is not an identity mapping — concretely, **Green Valley's approved mapping is `"2025" → "2024-25"` and `"2026" → "2025-26"`** (Phase 1.2D's `DECISIONS["greenvalley_demo"]["mapping"]`), so a direct `name=<legacy string>` lookup for a Green Valley row whose legacy value is `"2025"` would search for an `AcademicYear` named `"2025"` — which does not exist and never will, since no such row was ever approved — rather than resolving to the correct `AcademicYear` named `"2024-25"`. Sunrise Valley's mapping happens to be an identity mapping (`"2025-26" → "2025-26"`, `"2026-27" → "2026-27"`), which is exactly why this bug would have passed every Sunrise-only test while silently leaving every Green Valley row's FK null or wrong. The corrected algorithm, used identically by both the backfill (§4) and dual-write:

  ```
  def resolve_academic_year_fk(tenant, legacy_value):
      mapping = DECISIONS[tenant]["mapping"]           # the same approved, reviewed dict §4's backfill uses
      mapped_name = mapping.get(legacy_value)          # step 1: legacy string -> approved AcademicYear.name
      if mapped_name is None:
          return None, "unmapped"                      # legacy value has no approved mapping entry at all
      academic_year = AcademicYear.objects.filter(name=mapped_name).first()   # step 2: name -> row, in THIS tenant's schema
      if academic_year is None:
          return None, "mapped_name_missing_row"       # mapping says it should exist; it doesn't (data/setup gap)
      return academic_year, None
  ```

  Two failure modes, both already anticipated by gate 1 (§6) and both handled identically: **(a)** the legacy value itself has no entry in `DECISIONS[tenant]["mapping"]` (an unmapped value — same as a backfill-time unmapped row), and **(b)** the mapping has an entry but the corresponding `AcademicYear` row does not exist in this tenant's schema (should not happen given Phase 1.2D's rows are already created, but must not be assumed — checked explicitly, not trusted). **In either failure mode, dual-write preserves the current write behavior exactly (the legacy string field is written, nothing about that write changes) and leaves the FK `NULL`**, reporting the unresolved case through the same drift/validation reporting this plan already defines (§6 gate 1, §7 drift detection) — never by normalizing, reinterpreting, or guessing at the legacy string, and never by blocking or failing the write. This mirrors, rather than duplicates, the backfill's own resolution — **both paths must call the same `resolve_academic_year_fk()` function (or equivalent single source of truth)**, not two independently-written copies of the same two-step lookup, so the mapping semantics can never drift between backfill-time and write-time resolution.

  **Explicit planned tests for this resolution function** (in addition to the existing test-plan items in §10):
  - Green Valley: legacy `"2025"` resolves to `AcademicYear(name="2024-25")`; legacy `"2026"` resolves to `AcademicYear(name="2025-26")` — both asserting the mapped `AcademicYear.id`, not merely that *some* non-null FK was set, since a wrong-but-non-null FK is a worse failure than a null one.
  - Sunrise Valley: legacy `"2025-26"` resolves to `AcademicYear(name="2025-26")`; legacy `"2026-27"` resolves to `AcademicYear(name="2026-27")` — confirming the identity-mapping case works through the same two-step function, not a shortcut path.
  - Unknown legacy value (not present in `DECISIONS[tenant]["mapping"]` at all): resolution returns `None`, the write still succeeds with the legacy string set and FK left null, and the case is reported (not silently dropped).
  - Mapped name present in `DECISIONS[tenant]["mapping"]` but no matching `AcademicYear` row exists in that tenant's schema (simulate by temporarily deleting/renaming the row in a test fixture): resolution returns `None` with the distinct `"mapped_name_missing_row"` reason, write still succeeds, case still reported — distinguished from the "unmapped value" case in test assertions, even though both currently result in the same null-FK behavior, because they indicate different underlying problems (a missing mapping decision vs. a missing/corrupted `AcademicYear` row).

  If no resolution is possible (either failure mode), the FK is left `NULL` and the write still succeeds — **dual-write must never block or fail a write that would otherwise have succeeded today**, since the legacy field remains authoritative and gaining a null FK is not an error condition during this phase. This applies uniformly to all 13 fields, including `StudentFee` — see §6 gate 4's explicit resolution of why "require match" (Decision 1) and "never block" are not in conflict: this phase sets the FK independently without comparison to `FeeStructure`, and the comparison-based enforcement is a separate, later, separately-approved step.
- **Transaction boundaries**: the FK resolution and set must happen inside the same `transaction.atomic()` block as the legacy field write (not a separate follow-up call, which would reintroduce the exact race/inconsistency window a migration is supposed to eliminate). Each of the write-path functions identified in Phase 1.3A §10 (`_resolve_academic_year`, `bulk_enroll`, `publish_examination`, `assign_student_fee`, `StudentEnrollmentSerializer.create/update`, promotion's `execute_lifecycle_actions`, `validate_timetable_entry`'s accompanying create/update) needs this same two-line addition (set the string, then resolve+set the FK) inside its existing atomic block — this is the bulk of the actual code diff this phase produces.
- **Drift detection (corrected in this revision)**: a standing, read-only management command/report (extending `validate_tenant()`'s approach) that periodically (or on-demand) finds rows whose FK's `AcademicYear.name` does not equal the **mapped canonical name the shared resolver would produce for that row's legacy string** — i.e. `resolve_academic_year_fk(tenant, row.<legacy_field>)`'s result, not a bare `FK.AcademicYear.name == row.<legacy_field>` string comparison. **The bare comparison is wrong for exactly the same reason the original §7 resolution bug was wrong**: for Green Valley, a correctly-resolved row has legacy `"2025"` and `academic_year_ref` pointing to `AcademicYear(name="2024-25")` — a direct `AcademicYear.name == legacy_string` check would see `"2024-25" != "2025"` and incorrectly flag every correct Green Valley row as drifted, while a genuinely drifted row (FK pointing to the wrong year) could in principle produce a string that happens to differ in the expected way and pass unnoticed. The drift check must therefore go through the same `resolve_academic_year_fk()` function as backfill and dual-write (one shared source of truth, not a third independently-written comparison), comparing the row's actual `academic_year_ref_id` against what that function says it *should* be for the row's current legacy string value. This should be zero at all times once dual-write is live, and any non-zero count indicates a dual-write bug in one of the write paths above, not a data problem to patch around — and, with the corrected comparison, a non-zero count can no longer be a false positive produced by Green Valley's non-identity mapping.
- **Rollback behavior at every stage**: because the legacy field remains authoritative throughout, rolling back the dual-write code change (reverting the service-layer diff) at any point is purely a code rollback — no data repair is needed, since nothing ever depended on the FK being populated for correctness. This is the single most important rollback property of this design and is why "authoritative field" is decided first, before any other rollback question.

## 8. Compatibility with Existing API Request/Response Contracts

- **No existing request or response field is renamed, removed, or changes type in this phase.** Every serializer's `Meta.fields` keeps `academic_year` as a plain string, read and written exactly as today. `academic_year_ref` is not exposed in any serializer in this phase — it is an internal column only, populated by application code, not accepted as client input and not returned in any response.
- This directly satisfies Decision 5 (frontend stays untouched) without requiring a frontend change: since the API contract is unchanged, the existing frontend continues to function exactly as today, unaware the FK column exists.
- **Documented for the future frontend phase (not implemented here)**: once a future phase makes the FK authoritative, the eventual API contract will need either (a) to keep accepting/returning a string and resolve it server-side (no frontend change required, consistent with the "zero frontend integration today" finding in Phase 1.3A §3.7), or (b) to expose a proper `{id, name, start_date, end_date}` AcademicYear object as suggested by the existing `/academic-years/` list endpoint (Phase 1.2B), requiring frontend dropdown work. This plan documents both options exist and recommends option (a) as the lower-risk default for whatever phase picks this up, given the complete absence of any frontend readiness today — but does not choose between them, since that choice belongs to the frontend phase itself (Decision 5).
- **Existing readers/writers audited in Phase 1.3A** (views.py filters, admin `list_filter`, `filterset_fields`, the seeders) are all unaffected by adding a nullable column — Django's `filterset_fields`/query-param filters on the legacy string continue to work exactly as today; none of them need to change in this phase.

## 9. Constraint Strategy

- **All 13 FK fields are nullable (`null=True`) for the entire duration of Phase 1.3B** (the 13-row table in §2 already counts both of `PromotionRecord`'s two FKs — `source_academic_year_ref` and `target_academic_year_ref` — as separate rows #9 and #10, so 13 is the correct total, not 14). No `NOT NULL` constraint is added in this phase — that is explicitly Step F of the Phase 1.3A staged plan, gated behind a full dual-write observation window (Phase 1.3A §8 Step E), which is itself out of this phase's scope (this plan only covers through dual-write + validation, consistent with the mandatory constraints given for this prompt: "keep the legacy string columns until a separate phase... do not propose tightening constraints until validation proves it is safe").
- **No new `unique_together`/index is added onto any of the 13 FK fields in this phase** — the existing string-keyed uniqueness constraints (StudentLevel, SubjectEnrollment, Period, the 3 TimetableEntry tuples) remain the sole enforcement mechanism throughout Phase 1.3B, exactly as today, since the FK is not yet authoritative. Mirroring these constraints onto the FK is explicitly Step F's job (Phase 1.3A §4.1), not this phase's.
- **The one deliberate permanent exception**: `PromotionRecord.target_academic_year_ref` must remain nullable even after a hypothetical future Step F, because terminal promotion actions have no target year by design (confirmed in Phase 1.3A §3.5) — this plan flags it now so a future Step F author does not mistakenly treat every null as a migration gap.
- **The six Sunrise `2024-25` GradeBoundary rows (Decision 6)**: `academic_year_ref` stays `NULL` for exactly the six pinned primary keys listed in §4 — not "any six rows that happen to match a count." This plan adds an explicit, named regression test (§10) asserting that exact ID set stays null and that no other row anywhere in either included tenant is ever null for a reason other than an unresolved-mapping failure caught by gate 1 — so a future Step F author has an unambiguous, enforced signal of which nulls are the documented exception versus which nulls would represent a real gap requiring investigation before tightening.

## 11. Deployment and Rollback Runbook

Each stage has its own go/no-go gate — the next stage does not start until the current stage's gate passes, and every stage's rollback is independent (does not require rolling back a later stage first, since no later stage is live yet when an earlier one needs reverting).

**Stage A — Schema (nullable FK columns, 6 per-app migrations covering all 13 fields, per §3)**
- Deploy: apply the 6 migrations via the project's tenant-aware migrate command, across all tenant schemas (including excluded ones, per §3).
- Go/no-go gate: `manage.py check` clean; `makemigrations --check --dry-run` clean; the updated `test_existing_academic_year_columns_are_unchanged_and_no_fk_added` (and its 13-table extension) passes; no application code yet references the new columns, so no behavior change is possible — gate is purely "did the schema change land cleanly."
- **Rollback — unit of reversal, stated precisely**: reversing one of the 6 migrations is reversing that **entire app's** `AddField` set for this phase — for the 2 single-field apps (attendance, course_content), that is the same thing as reverting one field; for the 4 multi-field apps (examinations: 4 fields; fees: 2 fields; students: 3 fields; timetable: 2 fields), reversing the migration removes **all** of that app's new FK columns together, not one field while keeping its siblings (§3, §10). **This plan does not claim, and no later section should be read as claiming, that an individual field within a multi-field migration can be reverted independently of its siblings** — if that granularity is ever genuinely needed, it requires splitting that field into its own follow-up migration first (§3), not reversing part of an already-applied combined migration.
- **Rollback is permitted only under a reviewed runbook, and only when safe to do so**: reversing any Stage A migration is safe to execute at any time *while Stage A is the most recently completed stage and no later stage has run* (nothing reads or writes the column yet). It is **not** unconditionally safe once Stage B (backfill) or Stage D (dual-write) have executed — at that point the column holds real data and/or live application code depends on its presence, and reversing the migration would silently discard that data and could break the running application. A rollback decision at or after Stage B/D must go through an explicit, reviewed runbook step that confirms (a) no later-stage code or data currently depends on the column being present, and (b) the specific reason rollback is needed, before the migration is reversed — rollback of Stage A's schema is never treated as a routine, no-review action once later stages have built on it.
- **Not zero-downtime by assumption — verified**: `ALTER TABLE ADD COLUMN ... NULL` in PostgreSQL does not rewrite existing rows and takes only a brief metadata lock (confirmed behavior for nullable column addition with no default, PostgreSQL 11+), so this stage specifically is low-risk for lock duration — but this plan does not generalize that same confidence to Stage D (service-layer code deploy, which has normal rolling-deployment considerations: old and new app server versions running simultaneously during a rolling restart, addressed below) or Stage F (future constraint tightening, which DOES require a full table scan to validate and is explicitly deferred past this phase).

**Stage B — Backfill**
- Deploy: run `backfill_academic_year_fks` in dry-run mode first (mandatory), review the plan output, then run with `--apply`, tenant by tenant, table by table (not all 13 tables simultaneously, to bound the operational blast radius of any single table's issue).
- Go/no-go gate: gate 1 (unmapped rows) and gate 2 (six exceptions) from §6 both pass with the expected, pre-known counts; no table's backfill leaves any row both non-exception and unresolved.
- Rollback: `UPDATE <table> SET academic_year_ref = NULL` is always safe and always available (the legacy field is untouched throughout), but given idempotency (§4), the practical "rollback" for a backfill is simply "re-run it" after fixing whatever caused gate 1/2 to fail — a destructive null-out is a last resort, not the default rollback action.

**Stage B Rollback — Repairing an Already-Written Incorrect FK (new in Revision 9)**

The re-run-based "rollback" above only covers rows where `academic_year_ref IS NULL` (§5's idempotency gate) — it cannot detect or fix a row whose FK was already written to the *wrong* `AcademicYear`. That is a different, higher-risk situation and must never be handled as an ordinary re-run or folded into Stage B's normal operation. This gap was identified in review before any Stage B code exists; the procedure below is specified now so it is reviewed as part of the plan, not improvised during an actual incident.

**Repair procedure:**
1. **Diagnose, don't guess.** Before any write, identify exactly which rows are wrong and what the correct value should be via a read-only query that recomputes the expected FK using the same `resolve_academic_year_fk()` logic Stage B itself uses — never a manually-typed replacement value.
2. **Scope the repair to an exact, enumerated primary-key list** — never a broad `UPDATE ... WHERE <condition>`. This mirrors the same discipline already required for the six pinned `GradeBoundary` exceptions (§4): name the exact rows, not a filter that could silently widen to rows that were not actually wrong.
3. **Require its own explicit approval, separate from Stage B's own authorization** — phrased as its own authorization (e.g., "I authorize this repair for these N rows in this tenant/table only"), since a targeted data correction is not part of Stage B's original scope and should not be inferred from a general Stage B go-ahead.
4. **Before/after verification is mandatory**: snapshot the exact rows' FK values before the repair, apply the correction inside one `transaction.atomic()` block, then snapshot again and diff — confirming only the named rows changed and nothing else did.
5. **Audit-logged**, following `apply_tenant()`'s existing `AuditLog.objects.create(...)` convention (§4) — one entry per corrected row, recording both the incorrect and the corrected value.
6. **A broad `UPDATE ... SET academic_year_ref = NULL` is never a routine recovery action** — it remains available only as a last resort, and only under the same approval/scope/verification discipline as the repair itself, never as a default response to a failed gate.

This procedure is specified here as a plan requirement; it is not implemented in code by this revision, and nothing in this subsection is executed by writing it down.

**Stage C — Validation (the mismatch report, Decision 1)**
- Deploy: nothing deployed; this is a report-generation run.
- Go/no-go gate: the report itself is the gate's output, not a pass/fail in the usual sense — it blocks Stage D only in the sense that Stage D's dual-write code must be written with full knowledge of whatever mismatches this report found (so the "require match going forward" part of Decision 1 can be designed without being surprised by pre-existing cases it must not touch).
- Rollback: N/A (read-only).

**Stage D — Dual-write code (service-layer changes listed in §7)**
- Deploy: standard rolling deployment of the Django application code. **This is the one stage where "zero-downtime" needs honest scrutiny, not an assumption**: during a rolling restart, old app-server instances (not yet dual-writing) and new instances (dual-writing) run concurrently against the same database. Because the legacy field remains authoritative and the FK write is purely additive (old instances simply don't set it; new instances do), the write path itself is safe — a write from an old instance produces exactly today's behavior (string set, FK left null), which is a valid, already-anticipated state (§6 gate 1 already tolerates nulls from timing gaps). **This safety claim does not, by itself, mean the deployment is complete** — every row written during the mixed-version window is left with a null FK that nothing has yet gone back to resolve, and that gap must be explicitly closed, not left to be noticed later.
- **Explicit pre-condition verified before Stage D's deploy begins**: a repo-wide check confirming no serializer, view, report, or export anywhere reads `academic_year_ref` as authoritative or falls back to it — i.e. every one of the write-path locations in §7 is purely additive (sets the FK, never conditions behavior on it) and every read path (views.py filters, admin, reports) still reads only the legacy string field. This is not assumed from the design intent; it must be confirmed by a grep/review pass across the 6 touched apps immediately before Stage D's code is merged, precisely because a reviewer could otherwise assume "the plan says nothing reads it yet" without checking that the actual diff honors that.
- **Mandatory post-deployment step, part of Stage D itself, not a separate later phase**: once the rolling deployment completes (all instances running the new dual-write code), re-run the Stage B backfill command (§4/§5) once more — this catches every row written during the mixed-version window whose FK was left null purely because the writing instance hadn't yet been upgraded, using the exact same idempotent, `WHERE academic_year_ref IS NULL`-gated logic as the original backfill (no new code needed, just one more scheduled run).
- **Stage D go/no-go gate is two-part, not one**: (a) the standard regression gate — full existing test suite for all touched apps passes, a new dual-write-specific test per write path confirms correct FK-setting behavior (§10); **and** (b) the **post-deployment reconciliation gate** — after the mandatory re-run above, the drift-detection report (§7, using the mapped-canonical-name comparison, not a bare string-equality check) shows zero rows where a non-null legacy string has a null FK that SHOULD be resolvable (i.e., every row written during the mixed-version window has now been caught up by the re-run backfill) and zero rows where the FK disagrees with what `resolve_academic_year_fk()` says it should be. **Stage D is not considered complete, and no later phase should assume dual-write is fully reconciled, until gate (b) is confirmed green** — this is the explicit recovery step the original draft was missing: it described the write-path safety but not the closing step that actually finishes reconciling the mixed-version window's gap.
- Rollback: revert the application code deploy. No data repair required for the rollback itself (§7) — the FK column simply stops being written going forward; nothing reads it as authoritative (confirmed by the pre-condition check above), so no reader is affected. Any rows whose FK was already set by the reverted code are harmless and can be left as-is (they are correct, just no longer being added to).

**No Stage E or F in this phase.** Phase 1.3A's staged plan's Step E (production observation) and Step F (constraint tightening) remain explicitly future, separately-gated phases, consistent with the prompt's instruction not to propose tightening constraints until validation proves it safe, and consistent with this plan covering only through dual-write.
