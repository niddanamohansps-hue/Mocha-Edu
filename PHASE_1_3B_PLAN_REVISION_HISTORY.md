# Phase 1.3B — AcademicYear FK Migration Implementation Plan: Revision History

This file holds the full changelog for every revision of `PHASE_1_3B_IMPLEMENTATION_PLAN.md` (currently Revision 9). Split out on request because the combined file had grown large (425 lines); content is unchanged, only relocated — no wording was edited, reordered, or removed in this split.

This plan follows `PHASE_1_3A_ACADEMIC_YEAR_FK_MIGRATION_DESIGN_REPORT.md` (the audit) and is bound by every decision in `PHASE_1_3B_DECISIONS_RECORDED.md`. Where this plan narrows or defers something, it cites the governing decision by number rather than re-deciding it.

**Revision 1 changes**: resolved four review items raised against the initial draft — (1) separated the StudentFee/FeeStructure mismatch *report* (non-blocking, this phase) from *enforcement* (a separately gated future step), (2) replaced the "count of six" exception test with an exact, pinned predicate (tenant + table + primary keys), (3) consolidated migration granularity from 13 per-table files to 6 per-app files, (4) made the rolling-deployment recovery explicit with its own post-deployment backfill/drift-validation gate. The two open prerequisites from the initial draft were confirmed: **deployed PostgreSQL version is 18.4** (verified via `SHOW server_version` against the live dev database), and **`academic_year_ref` has zero naming collisions** anywhere in the repository (verified by repo-wide search).

**Revision 2 changes**: (1) **fixed a genuine correctness bug** in §7's dual-write design — it proposed resolving the FK by looking up `AcademicYear.name == <the legacy string value>` directly, which is wrong for Green Valley, where the approved mapping is `"2025" → "2024-25"` and `"2026" → "2025-26"` (the legacy string and the `AcademicYear.name` are different values by design for that tenant). Dual-write now resolves through `DECISIONS[tenant]["mapping"]` first, exactly as the backfill already does, never by assuming the legacy string equals the target name. (2) Corrected every stale reference to 12 or 13 migration files (§§10, 11, 12, 13) to match the already-revised 6-per-app design, and distinguished "reverse an app's whole migration" from "revert a single field" (the two are not the same operation once a migration holds multiple `AddField` operations). (3) Added an evidence-based locking/transaction strategy for the `StudentLevel.academic_year_ref` backfill, grounded in two facts confirmed by a targeted read-only check in this revision: `students/services.py`'s existing promotion code already locks `StudentLevel` rows via `select_for_update()` in stable ascending `student_id` order (a documented deadlock-avoidance discipline, matching `fees.services.record_payment`'s own convention), and the project's Postgres connection has **no** `lock_timeout`/`statement_timeout` configured anywhere (confirmed by reading `config/settings.py`'s `DATABASES` block) — meaning no existing retry/timeout convention exists to reuse, and the backfill must establish its own, scoped only to its own transactions. (4) Re-verified every other safety gate (pinned six-ID exception, read-only Stage C report, Stage D's pre-condition/mandatory-rerun/two-part gate, nullable FKs with `PROTECT`, no new uniqueness, no legacy-column removal, no frontend/API exposure) is still stated consistently throughout and was not weakened by the corrections above.

**Revision 3 changes**: two targeted refinements from a review of Revision 2's actual content (all four of that review's original items were confirmed already correctly addressed in Revision 2). (1) **Fixed a second instance of the same class of bug §7 had already fixed once**: the drift-detection report (§7) was still comparing `AcademicYear.name` against the raw legacy string directly, which would incorrectly flag every correctly-resolved Green Valley row as drifted (legacy `"2025"` correctly resolves to `AcademicYear(name="2024-25")` — those two strings are never equal, by design). Drift detection now compares a row's actual FK against what the shared `resolve_academic_year_fk()` function says it *should* be, not against the legacy string's literal text — the same fix applied to the exact same underlying mistake, this time in the validation path rather than the write path. (2) **Tightened §4.1's concurrency error handling** with three additions: error classification (retry only on the specific PostgreSQL lock-timeout/deadlock error codes, never a bare `except Exception`/`except OperationalError` that would also retry unrelated failures), retry-after-rollback ordering (the retry loop sits outside each attempt's `transaction.atomic()` block, never inside an already-poisoned transaction), and a same-rows guarantee (the batch's lock query and update query must operate on one materialized ID set computed once per attempt, not two independently-re-evaluated queries).

**Revision 4 changes**: closes the four preparation items requested before Stage A can be considered for separate authorization, and adds a new §15 recording exactly what was closed and what remains deliberately open. (1) **StudentFee/FeeStructure mismatch policy finalized for this phase's scope**: this phase produces the report only; enforcement is confirmed, explicitly and finally, to stay outside Phase 1.3B, gated behind a human review of that report's actual findings — there is nothing further for this plan to decide on this point, and §15 records it as closed. (2) **Shared resolver module location settled**: `resolve_academic_year_fk()` lives in `backend/academics/backfill.py`, imported by the 6 write-path apps — confirmed safe by directly checking `academics/backfill.py`'s own imports, which depend on nothing in any of those 6 apps, so the import direction (6 apps → academics, never the reverse) introduces no circular-import risk. (3) **Seeder dual-write dependency resolved: NOT required.** Checked directly against Phase 1.3A's per-field audit findings: every seeder (`seed_demo_school.py`, `seed_realistic_school.py`, `populate_test_data.py`) writes all 13 legacy fields via direct `.objects.create()`/`bulk_create()` calls, bypassing every one of the 7 dual-write locations in §7 entirely (serializers, services, the bulk_enroll/publish_examination/assign_student_fee functions). Dual-write code added to those 7 locations therefore cannot reach seeded data regardless of whether seeders change — seeded data's FK is populated the same way as any other pre-existing data: by Stage B's backfill (§4), which already covers it without touching a single seeder file. This closes Decision 4's named-blocker condition as never triggered. (4) **Per-stage acceptance criteria finalized** (§13, revised) into an explicit checklist per stage, citing the pinned six-ID GradeBoundary exception and the tenant-specific mapping tests by name rather than by cross-reference alone.

**Revision 8 changes** (Stage A has since been implemented, verified, and audited; this revision applied ONLY to §4.1's concurrency error classification, in response to a verified discrepancy found by the Pre-Stage-B Readiness Audit): §4.1's lock-timeout retry condition is corrected from `pgcode == '57014'` + message-text matching to **`pgcode == '55P03'`** (`psycopg2.errors.LockNotAvailable`) alone — verified live, safely, and non-destructively against this project's actual PostgreSQL 18.4 + psycopg2 2.9.13 stack in that audit (not re-verified in this revision, which only edits the written plan). The deadlock condition (`40P01`) is unchanged and unaffected. `57014` is now explicitly evaluated as its own case: confirmed (by the same audit) to be produced by `statement_timeout` expiry, and this plan does **not** classify any `57014` as retryable — whether a narrowly message-gated secondary `57014` condition should ever be added is left **explicitly unresolved**, not guessed at, since the available evidence (one verified scenario) is insufficient to decide it. Retry-after-rollback ordering, the bounded 3-attempt backoff policy, lock ordering, and the `SET LOCAL lock_timeout` requirement are all unchanged and reaffirmed. §10's concurrency test row is extended with explicit classifier-unit-test requirements (`55P03`→retry, `40P01`→retry, `57014`→no-retry, unrelated error→no-retry) alongside the existing end-to-end scenarios, plus a retry-exhaustion test. No application code, test, migration, or database record was changed to produce this revision — this is a plan-document-only correction.

**Revision 6 changes**: two final refinements before Stage A authorization. (1) **Count inconsistency fixed in §9**: "All 13 (14, counting PromotionRecord's two)" is corrected to plain "13" — the §2 table already counts both of `PromotionRecord`'s FKs (`source_academic_year_ref`, `target_academic_year_ref`) as separate rows #9 and #10 within the 13-row total; there was never a 14th field, only a confusing parenthetical. (2) **§4.1's message-text matching is now explicitly scoped as provisional, not a finished interface**: PostgreSQL's exact cancellation wording can vary by server version, locale, and driver wrapping, so this plan no longer asserts its proposed English substring as a guaranteed-stable signature. Before Stage B (not Stage A, which never reaches this code) is implemented, the plan now requires: verifying the actual exception type/pgcode/message this project's live PostgreSQL 18.4 + driver stack produces for a real contended lock (not assumed from documentation), isolating the check inside one small, independently unit-tested classifier function rather than inlining it per call site, and failing closed — an unrecognized cancellation always propagates, never defaults to retry.

**Revision 5 changes**: one narrow technical correction to §4.1's error classification, identified by reviewing the already-closed Revision 4 text. The prior wording treated bare SQLSTATE `57014` (`query_canceled`) as sufficient to identify a lock-timeout cancellation and retry it. **That is incorrect** — PostgreSQL raises the identical `57014` code for a `statement_timeout` expiring, an administrator's manual `pg_cancel_backend()`, or any other statement cancellation, not only for this batch's own `SET LOCAL lock_timeout` firing. Retrying on bare `57014` would therefore also retry (and mask) an unrelated cancellation that should instead propagate immediately. The corrected classification now requires **both** `pgcode == '57014'` **and** a message-text match on PostgreSQL's cause-specific wording (`"canceling statement due to lock timeout"`, distinct from its `"...due to statement timeout"` and `"...due to user request"` variants for the same SQLSTATE) before treating it as retryable; everything else — a bare `57014` without that exact text, any other `OperationalError`, a constraint violation, a connectivity failure, a programming error — propagates immediately, uncaught by the retry loop. The deadlock condition (`40P01`) is unaffected, since that SQLSTATE is already specific to deadlocks and needed no message-text check. This is a correction to the error-classification wording only — the retry-after-rollback ordering and same-rows guarantee added in Revision 3 are unchanged. Also added: an explicit statement at the top of §13's Stage A checklist confirming its scope is the 6 schema migrations only (not backfill, mismatch report, dual-write, or frontend work), consistent with — not separate from — §11's existing Stage A scope.
